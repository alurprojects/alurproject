# Audit ALUR — 2026-10-27

**Scope:** seluruh repo (backend FastAPI, web Next.js, mobile Flutter, supabase/migrations, konfigurasi deploy).
**Metode:** dibaca end-to-end jalur kritis: auth → API → services → agent graph → cron → DB; boundary trust, penulisan data, test, config deploy.

**Apa yang dilakukan repo ini:**
ALUR adalah as produktivitas berbasis AI. Web (Next.js) dan mobile (Flutter) mengirim chat/brain-dump ke backend FastAPI di Vercel serverless. Backend memakai LangGraph (companion → extractor → scheduler) untuk mengubah omongan jadi task terjadwal, menyimpan semuanya di Supabase Postgres (service-role key, RLS dilewati backend), dan menjalankan pekerjaan malam/mingguan lewat cron-job.org.

**Beban yang diasumsikan:** aplikasi tahap awal — satu developer, hosting Vercel free tier (limit 10s per request), pengguna ratusan, cron eksternal cron-job.org. Temuan dinilai terhadap beban ini.

## MUST FIX (sebelum launch publik)

### 1. `CRON_SECRET` punya default yang bisa dibaca siapa pun
`backend/app/core/config.py:24`
- **Apa ini:** Endpoint `/internal/cron/*` dilindungi header `X-Cron-Secret`. Nilai pembandingnya punya default hardcoded di repo: `alur-dev-cron-secret-2026`.
- **Masalah:** Kalau env `CRON_SECRET` lupa diisi di Vercel, siapa pun di internet bisa `POST /internal/cron/all` dengan secret yang ada di GitHub — memicu seluruh job LLM untuk semua user (biaya API, churn data, bahkan hard-delete conversation log).
- **Fix:** Ganti default jadi `""` — cek di `internal_cron.py:28` (`if not expected_secret`) sudah menolak secret kosong. Satu baris.
- **Kalau dilewati:** Amukan biaya LLM dan penghapusan data bisa dipicu orang luar tanpa akun.

### 2. Fallback auth dev + `BACKEND_ENV` default `"development"`
`backend/app/core/config.py:23` + `backend/app/api/deps.py:31-32`
- **Apa ini:** Request tanpa JWT valid ditolak — kecuali `BACKEND_ENV != "production"`, maka otomatis jadi user dev `00000000-0000-0000-0000-000000000001`.
- **Masalah:** Default-nya memang `"development"`. Deploy produksi yang lupa set `BACKEND_ENV=production` terbuka penuh: semua request tanpa token membaca/mengubah data user dev lewat client service-role (RLS dilewati). Gagalnya diam-diam, bukan 500.
- **Fix:** Balik defaultnya: `BACKEND_ENV: str = "production"`, dev meng-override eksplisit. Plus `logger.warning` tiap kali fallback dipakai.
- **Kalau dilewati:** Satu env var yang hilang = seluruh API terbuka tanpa auth.

### 3. "Hari ini" dihitung di UTC, bukan zona waktu user
`backend/app/services/cron_service.py:28,76,254` · `backend/app/agents/graph.py:96,181` · `backend/app/services/task_service.py:232`
- **Apa ini:** Nightly status check, recurrence generator, reflection, brain-dump, chat, dan follow-up "RESCHEDULED" semuanya pakai `date.today()` — jam server, yang di Vercel = UTC.
- **Masalah:** Cron nightly jalan 00:00 WIB = 17:00 UTC → `date.today()` masih "kemarin" WIB, jadi task hari kemarin user tidak di-mark MISSED sampai malam berikutnya (chip "terlewat" muncul telat 1 hari, statistik completion weekly jadi bias). Pesan "besok" yang diketik jam 00:00–07:00 WIB dijadwalkan ke tanggal yang salah, dan follow-up RESCHEDULED memindah task ke "hari ini" yang salah. Ironisnya `users.timezone` sudah ada dan morning brief sudah benar (`cron_service.py:546-558`).
- **Fix:** Satu helper kecil `today_for_user(user_id)` pakai `zoneinfo.ZoneInfo(user.timezone)` (default `Asia/Jakarta`), dipakai di keenam tempat itu.
- **Kalau dilewati:** Semua fitur harian ALUR (fokus hari ini, chip terlewat, jadwal) geser meleset untuk user WIB.

## SHOULD FIX

### 4. Perbandingan secret tidak timing-safe
`backend/app/api/internal_cron.py:28`
- **Apa ini:** `x_cron_secret != expected_secret` dibandingkan string biasa.
- **Masalah:** Rentan timing attack teoretis pada header secret.
- **Fix:** `secrets.compare_digest(x_cron_secret, expected_secret)`. Satu baris, sekalian dengan #1.
- **Kalau dilewati:** Risiko kecil, tapi perbaikannya gratis.

### 5. Cron menulis per-baris (N+1) dan akan terpotong timeout Vercel
`backend/app/services/cron_service.py:57-60, 369-372, 397, 421-454`
- **Apa ini:** Nightly check melakukan satu UPDATE per task overdue; retention notify satu UPDATE per log; hard-delete satu DELETE per log; memory condenser 2 query per user tanpa batch state.
- **Masalah:** Di serverless 10 detik, ratusan baris = run terpotong di tengah tanpa tanda; hanya `weekly-reflection` yang punya `cron_batch_state`, jadi sisanya diam-diam tidak selesai.
- **Fix:** Batch via `.in_("id", ids)` untuk update/delete, dan beri batch state ke nightly + condenser (pola sudah ada).
- **Kalau dilewati:** Makin banyak user, makin banyak task yang tidak pernah diproses per malam.

### 6. `ai_insights` bisa duplikat — tidak ada UNIQUE per (user, minggu, tipe)
`backend/app/services/cron_service.py:224-236` + skema `DATABASE.md` §8
- **Apa ini:** Reflection menyisipkan insight `WEEKLY_REFLECTION` per goal; batch state hanya mencegah duplikat dalam hari yang sama.
- **Masalah:** Job dipicu dua hari berbeda dalam minggu yang sama (mis. endpoint `all`) → insight ganda untuk pekan yang sama; tabel `morning_briefs` dan `embeddings` sudah punya unique index, tabel ini tidak.
- **Fix:** `CREATE UNIQUE INDEX ... ON ai_insights (user_id, week_of, insight_type)` + upsert `on_conflict`.
- **Kalau dilewati:** Feed insight user penuh pengulangan, biaya LLM terbuang.

### 7. `handle_reschedule` bisa 500 dan tidak atomik
`backend/app/services/task_service.py:316-323, 290-301`
- **Apa ini:** ACCEPT memindahkan task lalu menandai suggestion; hasil dibaca ulang tanpa cek kosong.
- **Masalah:** `task_id` tidak cocok (suggestion valid) → `updated_res.data[0]` = IndexError → 500. Kalau write kedua gagal, task sudah pindah tapi suggestion tetap PENDING (bisa di-accept lagi).
- **Fix:** Cek `updated_res.data` sebelum index; tulis suggestion dulu atau validasi pasangan task–suggestion.
- **Kalau dilewati:** 500 misterius + suggestion zombie yang bisa double-accept.

### 8. Test CRUD menulis ke Supabase sungguhan
`backend/tests/test_tasks.py`, `test_fase3.py`, `test_brain_dump.py`
- **Apa ini:** Test pakai `TestClient` tanpa override dependency; lewat fallback dev (#2) mereka insert/update/delete data user dev di DB live.
- **Masalah:** Tidak hermetic — hasil tergantung isi DB, bisa saling tabrakan, dan mengotori data dev bersama. Pola mock yang benar sudah ada di `test_chat.py` (`dependency_overrides`).
- **Fix:** Samakan pola `test_chat.py` untuk ketiga file itu.
- **Kalau dilewati:** Test gagal/acak tanpa ada bug, dan data dev berantakan.

### 9. JWT diduplikasi ke localStorage
`web/lib/supabase-browser.ts:23-27` + `web/lib/api.ts:74-79`
- **Apa ini:** Token disimpan di `localStorage['alur_jwt']` untuk dipakai `fetchAPI`, di samping session cookie SSR yang sudah ada.
- **Masalah:** localStorage terbaca skrip apa pun — satu XSS = token curian.
- **Fix:** `getAuthHeaders()` ambil token via `supabase.auth.getSession()` (client sudah ada), lalu hapus localStorage.
- **Kalau dilewati:** Permukaan XSS klasik yang mudah ditutup.

### 10. Migrasi 008–011 hilang — DB fresh dari repo tidak jalan
`supabase/migrations/` (001–007, 012–017) vs kode yang memakai `conversation_logs`, `cron_batch_state`, kolom `pending_deletion_notified_at`/`retention_override`, RPC `users_active_this_week`; `DATABASE.md:728` menyebut `008_create_ai_insights.sql` yang tidak ada di repo
- **Apa ini:** Tabel/kolom yang dipakai backend tidak punya file migrasi di repo.
- **Masalah:** Setup DB baru (atau rebuild) dari repo → backend mati saat query tabel yang tidak ada. Skema produksi dan repo sudah beda.
- **Fix:** Tambahkan migrasi yang hilang (atau dump skema) supaya repo = sumber kebenaran.
- **Kalau dilewati:** Disaster recovery / onboarding dev baru tidak memungkinkan.
